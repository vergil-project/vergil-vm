# Port-forward relay: idle reaping via socat (issue #298)

## Problem

The `port_forwards` relay generated by `templates/provision/80-port-forwards.sh`
is a socket-activated `systemd-socket-proxyd` `.socket`/`.service` pair. It
**leaks connections on abrupt client disconnect mid-transfer**: a client that
vanishes without draining its receive window leaves the proxy socket in TCP
zero-window **persist** state, holding both file descriptors and ~600 KB of
Send-Q memory. TCP keepalive never applies in persist, and `systemd-socket-proxyd`
exposes no idle-timeout / `TCP_USER_TIMEOUT` knob, so the connection leaks
**forever**. Under sustained real use (observed: ~18h of Grafana browsing) the
relay climbs to the soft `NOFILE` limit (1024) and then accepts-but-resets every
new connection — the unit reports `active` while every client fails.

This is distinct from the two failures already fixed in the generated unit:
the respawn-storm rate-limiter trip (`StartLimitIntervalSec=0`, #192) and the
downstream-restart wedge (`Restart=always`, #192). Neither reaps a half-dead
connection, so neither covers this fd/socket-buffer exhaustion.

Raising `LimitNOFILE` only moves the wall — socket-buffer memory still leaks
unbounded — so the cure must be a proxy that **reaps** stuck connections.

## Decision

Replace `systemd-socket-proxyd` with **`socat`** running as a long-lived,
forking service with an inactivity timeout:

```
/usr/bin/socat -T <idle> TCP-LISTEN:<port>,bind=0.0.0.0,fork,reuseaddr TCP:<to>
```

Two independent protections:

1. **`-T <idle>`** terminates any connection whose data channel is silent (both
   directions) for `<idle>` seconds. This reaps the zero-window-persist wedge
   within `<idle>` and frees its Send-Q memory. **This is the cure.**
2. **`fork`** isolates every connection in its own child process, so a single
   wedged connection can never exhaust the whole relay's descriptors the way it
   does with proxyd's single process — a structural second layer.

`<idle>` = **120 s**. Comfortably above any normal request/response gap or live
panel heartbeat (so it never disrupts legitimate traffic — and a dropped idle
keep-alive is transparently reopened by the client anyway), far below the
"leaks forever" status quo. It caps accumulation to a 120 s window. Defined as a
single constant at the top of the generator for easy retuning.

Alternatives rejected:

- **nginx `stream {}` + `proxy_timeout`** — same cure, but pulls in nginx plus a
  generated per-forward config file and more surface. Disproportionate for a
  dev-VM relay.
- **Keep proxyd + `LimitNOFILE` (+ reaper)** — proxyd has no timeout to add and
  the socket-buffer leak stays unbounded; NOFILE only moves the failure.

## Consequences

### Relay unit shape (`80-port-forwards.sh`)

- **Drop the socket-activation `.socket` unit.** `socat` binds `0.0.0.0:<port>`
  directly. The `0.0.0.0` bind — the precondition for Lima's auto-forward to the
  Mac — is preserved via `bind=0.0.0.0`.
- Keep one `.service` per forward, now `ExecStart=` the `socat` line above, with
  `Restart=always` + `RestartSec=100ms` + `StartLimitIntervalSec=0` retained
  (the #192 hardening still applies to the parent listener).
- `enable --now` the `.service` (was the `.socket`); a port already in use still
  aborts the build loudly (#130).
- No `LimitNOFILE` / `max-children` added: `fork` + `-T` remove the single-process
  exhaustion mode structurally, so bounding it would imply a failure mode that no
  longer exists (YAGNI). `max-children` remains an available hard-ceiling knob if
  a future need arises.

### Base image (`10-base.sh`)

Add `socat` to the first-boot `apt-get install --no-install-recommends` list
(Ubuntu `main`, tiny).

### Tests

- **`tests/test_port_forwards.sh`** — count `vergil-portforward-*.service`
  units instead of `*.socket`; the two-sided count contract is unchanged.
- **`tests/e2e-port-forwards.sh`** — assert the `.service` (not `.socket`) is
  active; keep the `ss -ltn | 0.0.0.0:<port>` bind check; grep the
  `socat … TCP:<to>` line (was `systemd-socket-proxyd <to>`); retarget the
  restart-storm `pkill` from `systemd-socket-proxyd <to>` to the `socat` parent.
  The downstream-restart (5a) and restart-storm (5b) recovery cases stay — they
  remain the regression guards and must pass under `fork` + `Restart=always` +
  `StartLimitIntervalSec=0`.

### Out of scope (follow-up)

- vergil-tooling `src/vergil_tooling/lib/config.py` has a comment describing
  forwards as relayed "via systemd-socket-proxyd" — it goes stale with this
  change. That is a one-line doc nit in a **different repo**; track it as a small
  follow-up issue rather than folding a cross-repo edit into this PR.
